# Testing

Test cases of the module: one for the main flow of each use case and one for each alternative flow. They can be run by hand on the web and in the app; the automated tests column shows which tests exercise the use case.

## Test cases

| ID | Use case | Steps | Expected result |
|---|---|---|---|
| `CP-EVT-01` | [`UC-EVT-01`](use-cases/uc-evt-01-discover-events.md) | 1) The person opens Events. 2) If they shared their location and applied no filters, the client calls `GET /events/discovery` with a 100 km radius and up to 50 events. 3) The API returns the nearby events and, separately, other current events outside the radius. 4) The client shows the nearby ones and then the others, with date, place, type and price. | The person sees the current events, nearby ones first if they shared their location. |
| `CP-EVT-02` | [`UC-EVT-01`](use-cases/uc-evt-01-discover-events.md) | Main flow → 2a. Without a location or with text, type, country or region filters | The client calls the paged `GET /events` with those filters. |
| `CP-EVT-03` | [`UC-EVT-01`](use-cases/uc-evt-01-discover-events.md) | Main flow → 2b. On the app, the person searches for an area | The app geocodes it and calls `GET /events/nearby` with a 100 km radius. |
| `CP-EVT-04` | [`UC-EVT-01`](use-cases/uc-evt-01-discover-events.md) | Main flow → 3a. There are no nearby events | Only the other events are shown, without presenting them as nearby. |

On the app, events with coordinates are also shown on a map, centered at a nearby zoom (about 30 km) on the searched area, the person's location or the first event. | On the app, events with coordinates are also shown on a map, centered at a nearby zoom (about 30 km) on the searched area, the person's location or the first event. |
| `CP-EVT-07` | [`UC-EVT-02`](use-cases/uc-evt-02-view-event.md) | 1) The client calls `GET /events/{id}`. 2) The API returns the event if it was published at least once and is not a draft. 3) The client shows image, description, date, place, organizer, price and places. 4) It offers opening the location in maps, contacting the organizer by web, email or phone if provided, sharing the event when it has a public page, and reporting it. 5) If the person already has a registration, the client fetches it with `GET /events/{eventId}/registrations/me` and shows its status. | The person sees the event and the available actions. |

| `CP-EVT-11` | [`UC-EVT-03`](use-cases/uc-evt-03-register-for-event.md) | 1) The person chooses “Reserve” on the event details. 2) The client asks for the number of tickets, up to the event's maximum per request, and a contact phone; name and email come from the account. 3) The person can save the phone to their profile and sees the total to pay if the event is paid. 4) The client sends `POST /events/{eventId}/register` with the count, the contact and the notice language. 5) The API locks the event, checks that registration is open and that the person has no other active one, and applies the capacity. 6) The API stores the registration with the matching status and notifies the person and the organizer ([UC-EVT-09](use-cases/uc-evt-09-attendee-notices.md)). 7) The client shows the status: requested, waitlisted, awaiting payment, awaiting confirmation or confirmed. | The person has a registration with its actual status. |

| `CP-EVT-14` | [`UC-EVT-03`](use-cases/uc-evt-03-register-for-event.md) | Main flow → 5c. The count exceeds the maximum per request | The API answers `REGISTRATION_LIMIT_EXCEEDED`. |

| `CP-EVT-22` | [`UC-EVT-04`](use-cases/uc-evt-04-confirm-attendance.md) | Main flow → 4a. The hold expired | The API answers 400 `REGISTRATION_HOLD_EXPIRED`. |

| `CP-EVT-45` | [`UC-EVT-09`](use-cases/uc-evt-09-attendee-notices.md) | Main flow → 5a. The person blocked the organizer, is the organizer or turned the category off | They get no notice. |
