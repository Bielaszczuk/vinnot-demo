# Testing

Test cases of the module: one for the main flow of each use case and one for each alternative flow. They can be run by hand on the web and in the app; the automated tests column shows which tests exercise the use case.

## Test cases

| ID | Use case | Steps | Expected result |
|---|---|---|---|
| `CP-LEG-01` | [`UC-LEG-01`](use-cases/uc-leg-01-legal-centre.md) | 1) The person opens the legal centre (`/legal`, on the web and in the app). 2) The client lists the documents: terms, privacy, content policy, moderation, trust and safety, ranking, payments and cancellations, and cookies. 3) The person picks one. 4) For the terms, the client asks the API for the current version in the interface language; the other documents ship with the client. 5) The client shows the document with its version. | The person read the document; reading records no acceptance. |
| `CP-LEG-02` | [`UC-LEG-01`](use-cases/uc-leg-01-legal-centre.md) | Main flow → 4a. The API does not answer for the terms | The copy bundled with the client is shown, marked as unconfirmed, with an option to reload. |
| `CP-LEG-03` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | 1) The person opens sign-up and the client loads the current terms. 2) The client shows the terms folded, the box unchecked and the link to the privacy policy. 3) The person can expand the text and checks the box. 4) When submitting sign-up, the client adds `termsAcceptance` with version, language, hash and `accepted: true`. 5) The API compares the selection with the current version before creating the account. 6) The API creates the account and stores the acceptance in the same transaction ([UC-USR-01](../users/use-cases/uc-usr-01-sign-up.md)). | The acceptance is stored with version, language and hash, in the same transaction that creates the account. Accepting the terms does not enable optional cookies or promotional messages. |
| `CP-LEG-04` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Main flow → 1a. The terms do not load | A "Reload terms" notice is shown and sign-up cannot be sent. |
| `CP-LEG-05` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Main flow → 3a. The box is not checked | The form is not sent. |
| `CP-LEG-06` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Main flow → 5a. The version or hash is no longer current | The API answers 422 `TERMS_VERSION_CHANGED`, does not create the account, and the client shows a translated message, reloads the terms and clears the box. |
| `CP-LEG-07` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Main flow → 1b. The person signs up with Google or Apple from that screen | No terms are sent and they are asked for after sign-in ([UC-LEG-04](use-cases/uc-leg-04-accept-current-version.md)). |
| `CP-LEG-08` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | 1) The person enters a private part of the application or the complete-profile step. 2) The terms gate asks the API for the acceptance status. 3) While waiting it shows "Checking your account…". 4) The API works out the status: if the account accepted the current revision, nothing is needed; if it accepted an earlier revision and the notice period has not ended, nothing is needed either, and the deadline (`requiredFrom`) is reported; otherwise acceptance is required. 5) If no acceptance is needed, the client shows the application. | The client knows whether the terms must be accepted; the application is shown only when they need not be. |
| `CP-LEG-09` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Main flow → 4a. Acceptance is required | Continue with [UC-LEG-04](use-cases/uc-leg-04-accept-current-version.md). |
| `CP-LEG-10` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Main flow → 2a and 2b. The check fails | With no connection or a timeout, the app shows "No connection" with an illustration and "Try again"; for any other reason, "We couldn't verify your agreement" with an option to reload. The application is never shown and missing terms are not assumed. |
| `CP-LEG-11` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Main flow → 1a. The person opens the legal centre or contact | Acceptance is not checked (the web exempts those routes; in the app they sit outside the private `(app)` group). |
| `CP-LEG-12` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | 1) The client shows "Before we continue" with the terms folded and the box unchecked. 2) The person checks the box. 3) They press "Accept and continue". 4) The client sends version, language, hash and `accepted: true`. 5) The API compares the selection with the current version and stores the acceptance. 6) The API returns the confirmed status and the client shows the application. | The acceptance is stored with account, revision, version, language, hash and a date set by PostgreSQL. Access opens only after the API confirms, and it holds on every platform. |
| `CP-LEG-13` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Main flow → 5a. The version changed meanwhile | The API answers 422 `TERMS_VERSION_CHANGED`, the client clears the box and asks to reload; it never retries the acceptance on its own. |
| `CP-LEG-14` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Main flow → 4a. The network fails | The error is shown with "Reload terms" and access stays closed. |
| `CP-LEG-15` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Main flow → 5b. The revision was already accepted (another device or a double submit) | The API duplicates nothing, keeps the first date and language and returns the status. |
| `CP-LEG-16` | [`UC-LEG-05`](use-cases/uc-leg-05-decline-and-sign-out.md) | 1) The person presses "Not now · sign out". 2) The client signs out ([UC-USR-08](../users/use-cases/uc-usr-08-sign-out.md)). 3) The person goes back to the public area. | The session is closed and no acceptance is recorded. The legal centre and contact stay available. |
| `CP-LEG-17` | [`UC-LEG-05`](use-cases/uc-leg-05-decline-and-sign-out.md) | Main flow → 2a. Signing out fails | "Please try signing out again." is shown. |
| `CP-LEG-18` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | 1) The scheduled task runs 60 seconds after start-up and then every 300 seconds. 2) It reads the current version and works out its deadline. 3) It locks the revision cursor and fetches the next 500 accounts to notify, ordered by id. 4) It queues one `TERMS_UPDATED` notice per account with the idempotency key `terms-updated:<revision>:<account>`. 5) It saves the last notified account as the new cursor. 6) The [notifications](../notifications/README.md) module sends the email with the `terms_updated` template. | Every active, unlocked account that accepted an earlier revision, and not the current one, gets a single `TERMS_UPDATED` notice with the version and the deadline. Progress is saved in `legal_terms_announcements`. |
| `CP-LEG-19` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | Main flow → 2a. There is no deadline or it has passed | The task does nothing. |
| `CP-LEG-20` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | Main flow → 3a. Fewer than 500 accounts remain | The revision is marked complete and later runs stop looking. |
| `CP-LEG-21` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | 1) The client calls a signed-in endpoint. 2) The interceptor checks the account's acceptance status. 3) If no acceptance is needed, the request goes on normally. | Accounts that must accept cannot use the signed-in API until they do. |
| `CP-LEG-22` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Main flow → 3a. Acceptance is required | The API answers 422 `TERMS_ACCEPTANCE_REQUIRED` ("Review and accept the current terms to continue"). |
| `CP-LEG-23` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Main flow → 1a. The route is exempt (`/auth/**`, `/legal/**`, `/support/**`, `/notifications/unsubscribe`, health, API docs and `/uploads/**`), the request is anonymous or it is `OPTIONS` | It passes without a check. |
| `CP-LEG-24` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Main flow → 1b. It is `DELETE /users/me` or `DELETE /users/me/permanent` | It passes without a check. |
| `CP-LEG-25` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | 1) The team writes a Flyway migration that inserts the `es` and `en` rows into `legal_documents` with the same version and revision, and the SHA-256 of each text. 2) They deploy the backend and the migration runs. 3) They set `LEGAL_TERMS_VERSION` to the new version. 4) The clients receive the new version when they ask for the terms. | The new version is archived and becomes current. If the contractual revision changed, accounts must accept again as in [UC-LEG-03](use-cases/uc-leg-03-check-acceptance.md). |
| `CP-LEG-26` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | Main flow → 1a. It is an equivalent editorial fix | A new version is published with the same revision and nobody has to accept again. |
| `CP-LEG-27` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | Main flow → 1b. It is a substantive change | A new revision is used; accounts that accepted the earlier one get the notice period and receive [UC-LEG-06](use-cases/uc-leg-06-announce-terms-update.md). |
