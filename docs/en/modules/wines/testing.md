# Testing

Test cases of the module: one for the main flow of each use case and one for each alternative flow. They can be run by hand on the web and in the app; the automated tests column shows which tests exercise the use case.

## Test cases

| ID | Use case | Steps | Expected result |
|---|---|---|---|
| `CP-WIN-01` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | 1) The person opens "Wines". 2) On first entry the client suggests the country of the device location, waiting up to 10 seconds. 3) The person types some text and picks type, grape, country or region. 4) The client waits for 400 ms without changes and calls `GET /wines` with the text, the filters and pages of 20. 5) The API validates the query and searches the active wines. 6) The client shows cards with name, winery, type, image and rating, and the total. | The active wines matching the text and filters are shown, with the total. |
| `CP-WIN-02` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 3a. The text has fewer than 2 characters | It is not sent and the catalog stays. |
| `CP-WIN-03` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 2a. There is no location permission or it does not answer | The global catalog is shown. |
| `CP-WIN-04` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 3b. The person changes the country | The chosen region is cleared. |
| `CP-WIN-05` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 3c. The person clears the filters | The unfiltered catalog comes back and the declined country is not suggested again. |
| `CP-WIN-06` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 5a. A text longer than 512 characters answers 422 `INVALID_SEARCH`. | A text longer than 512 characters answers 422 `INVALID_SEARCH`. |
| `CP-WIN-07` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 6a. There are no results | The empty state is shown. On the app it offers “Add your wine”, which opens the scanner to propose the wine with the searched text as its name ([UC-WIN-07](use-cases/uc-win-07-submit-wine.md)), and “Clear” when there are filters. |
| `CP-WIN-08` | [`UC-WIN-01`](use-cases/uc-win-01-search-catalog.md) | Main flow → 6b. The query fails | The error state is shown. |
| `CP-WIN-09` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | 1) On the web, the person moves to the next or previous page; in the app, they reach the end of the list. 2) The client asks for the next page of 20 with the same criteria. 3) The API returns the page with `hasNext`, `hasPrevious` and `totalPages`. 4) On the web the page is replaced and the URL keeps `page`; in the app the cards are appended without repeating wines. | The requested page is shown with the same criteria. |
| `CP-WIN-10` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | Main flow → 1a. On the web, the previous page stays on screen while the new one arrives. | On the web, the previous page stays on screen while the new one arrives. |
| `CP-WIN-11` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | Main flow → 1b. In the app no other page is requested while one is loading, when there is no next one or after an error. | In the app no other page is requested while one is loading, when there is no next one or after an error. |
| `CP-WIN-12` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | Main flow → 1c. In the app, pulling down reloads the first page and the list is replaced only when the load succeeds. | In the app, pulling down reloads the first page and the list is replaced only when the load succeeds. |
| `CP-WIN-13` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | Main flow → 1d. The criteria or the account change | It goes back to page 0. |
| `CP-WIN-14` | [`UC-WIN-02`](use-cases/uc-win-02-page-catalog.md) | Main flow → 3a. The requested page goes past the first 500 results | The API answers 400 `PUBLIC_CATALOG_WINDOW_EXCEEDED`. |
| `CP-WIN-15` | [`UC-WIN-03`](use-cases/uc-win-03-view-wine-detail.md) | 1) The person opens a wine from the catalog, the home screen or another module. 2) The client calls `GET /wines/{id}`. 3) The API loads the wine, its winery with the origin and the summary of the saved profile. 4) The client shows the wine data (description in the interface language, winery and origin, grapes, alcohol and rating) and the sensory summary, kept apart from the reviews and the AI profile. 5) It offers going to the winery, comparing, sharing and adding to the cellar. | The wine's page is shown; reading it does not generate an AI profile. |
| `CP-WIN-16` | [`UC-WIN-03`](use-cases/uc-win-03-view-wine-detail.md) | Main flow → 3a. The wine does not exist, or it is inactive and the reader is neither catalog staff nor its creator | The API answers 404 and the client shows it was not found. |
| `CP-WIN-17` | [`UC-WIN-03`](use-cases/uc-win-03-view-wine-detail.md) | Main flow → 4a. A field is missing | That block is not shown and no value is made up. |
| `CP-WIN-18` | [`UC-WIN-04`](use-cases/uc-win-04-scan-invitation.md) | 1) The person opens `/wines/scan`. 2) The web shows the invitation to download the app to scan labels. | The person knows scanning lives in the app and how to download it. |
| `CP-WIN-19` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | 1) The person opens the scanner from the home screen or from "Wines". 2) The app asks for camera permission. 3) The person frames the label and takes the photo; the image freezes. 4) The app checks resolution, light and focus, crops and saves the photo as JPEG up to 1600 px. 5) The app reads the label text on the device (up to 24 lines of 120 characters and 2000 in total). 6) The app sends `POST /wines/scan` with the photo and the text read. 7) The API validates the photo, first searches the catalog with the text read and, without an exact match, recognizes the label with OpenAI and searches again. 8) The API answers `EXACT_MATCH`, `POSSIBLE_MATCHES` (up to 3) or `NO_MATCH`. 9) With an exact match, the app shows the wine with "View details"; with suggestions, the person picks one; without matches, it offers searching by hand or proposing the wine. | The person sees the recognized wine, up to three suggestions or the option to search for or propose the wine. Scanning does not store the photo in the catalog. |
| `CP-WIN-20` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 2a. The person denies camera permission | The app explains it is needed to scan. |
| `CP-WIN-21` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 4a. The photo is dark, too bright, out of focus or low resolution | The app says so and asks for another shot. |
| `CP-WIN-22` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 7a. More than 18 seconds pass | The API answers 503 `LABEL_SCAN_TIMEOUT` and the app reports the delay, keeps the photo and offers retrying, searching by hand or taking another one. |
| `CP-WIN-23` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 7b. Recognition is unavailable or not configured | The app says so and keeps the photo. |
| `CP-WIN-24` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 6a. The person went over 30 scans in the hour | The API answers 429 and the app explains that the scan limit was reached and suggests waiting a few minutes or searching for the wine by name, keeping the photo. |
| `CP-WIN-25` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 1a. The person cancels or leaves | The app drops late answers and deletes only the temporary files it created. |
| `CP-WIN-42` | [`UC-WIN-05`](use-cases/uc-win-05-scan-label.md) | Main flow → 7c. The API rejects the photo or the read text, or is processing too many images | The app shows its own message for each case and keeps the photo. |
| `CP-WIN-26` | [`UC-WIN-06`](use-cases/uc-win-06-manual-search-from-scan.md) | 1) The person picks "Search by hand". 2) They type at least 2 characters. 3) The app waits for 300 ms without changes and searches the catalog for up to 10 wines. 4) The person picks a wine and the app opens its detail. | The person opens the wine they searched for, or goes on with the photo they took. |
| `CP-WIN-27` | [`UC-WIN-06`](use-cases/uc-win-06-manual-search-from-scan.md) | Main flow → 3a. The person changes the text | The previous results are discarded. |
| `CP-WIN-28` | [`UC-WIN-06`](use-cases/uc-win-06-manual-search-from-scan.md) | Main flow → 3b. There are no results | The app offers to propose the wine ([UC-WIN-07](use-cases/uc-win-07-submit-wine.md)). |
| `CP-WIN-29` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | 1) The person chooses to propose the wine and the app opens the form with the photo. 2) They fill in wine name and winery, and can add type, vintage, grapes, country, region, alcohol and notes. 3) The app validates and sends `POST /wines/submissions` with the data and the photo. 4) The API validates the photo, recognizes the label, combines what it recognized with the form, locks name, winery and vintage, looks for duplicates and moderates text and image. 5) If everything is safe and the wine is new, it publishes it in the catalog and answers 201 `APPROVED`. 6) The app shows the result. | A proposal is stored with status `APPROVED`, `DUPLICATE` or `NEEDS_REVIEW`. With `APPROVED` the wine is already in the catalog; with `DUPLICATE` the proposal points to the existing wine. |
| `CP-WIN-30` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | Main flow → 5a. The same wine already exists | It answers 202 `DUPLICATE` with the existing wine and, if it lacked an image and it is safe, uses the photo. |
| `CP-WIN-31` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | Main flow → 5b. Validation is incomplete or unsafe, or the provider is unavailable | It stores the photo in quarantine and answers 202 `NEEDS_REVIEW`; moderation decides ([Administration](../admin/README.md)). |
| `CP-WIN-32` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | Main flow → 3a. Name or winery is missing, or a value is out of range | The form is not sent. |
| `CP-WIN-33` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | Main flow → 3b. The person went over 10 proposals in the day | The API answers 429. |
| `CP-WIN-43` | [`UC-WIN-07`](use-cases/uc-win-07-submit-wine.md) | Main flow → 1a. From “Add your wine” the person does not have the bottle with them and taps “Add without a photo” | The form opens without a photo and says “Without a photo, an administrator checks the wine before it is published.”; the app sends no `image` part and the API skips recognition, moderation and image storage: when the form matches a wine exactly it answers 202 `DUPLICATE` without adding an image, otherwise 202 `NEEDS_REVIEW` with the `LABEL_PHOTO_MISSING` reason. |
| `CP-WIN-34` | [`UC-WIN-08`](use-cases/uc-win-08-attach-label-photo.md) | 1) The app offers to add the photo to the wine. 2) The person accepts and the app sends `POST /wines/{id}/label-image` with the photo. 3) The API recognizes the label again and requires the exact match to be that same wine. 4) It moderates the image, stores it as JPEG up to 1600 px and publishes it checking the wine's version. 5) It answers `attached: true` with the URL and the app shows the image. | The photo is published as the wine's image. |
| `CP-WIN-35` | [`UC-WIN-08`](use-cases/uc-win-08-attach-label-photo.md) | Main flow → 3a. The wine already has an image | It answers `attached: false` and changes nothing. |
| `CP-WIN-36` | [`UC-WIN-08`](use-cases/uc-win-08-attach-label-photo.md) | Main flow → 3b. The label does not belong to that wine | It answers `LABEL_IMAGE_WINE_MISMATCH`. |
| `CP-WIN-37` | [`UC-WIN-08`](use-cases/uc-win-08-attach-label-photo.md) | Main flow → 4a. Moderation does not approve the image | It answers `LABEL_IMAGE_REVIEW_REQUIRED`. |
| `CP-WIN-38` | [`UC-WIN-08`](use-cases/uc-win-08-attach-label-photo.md) | Main flow → 2a. The person went over 10 photo uploads in the day | The API answers 429. |
| `CP-WIN-39` | [`UC-WIN-09`](use-cases/uc-win-09-track-submissions.md) | 1) The person opens "My submitted wines" from Profile. 2) The app calls `GET /wines/submissions` with paging. 3) The API returns only that person's proposals, newest first. 4) The app shows status (`PENDING`, `APPROVED`, `DUPLICATE`, `NEEDS_REVIEW`, `REJECTED` or `CHANGES_REQUESTED`), reason and linked wine. | The person sees each proposal's status, the reason and the resulting wine. |
| `CP-WIN-40` | [`UC-WIN-09`](use-cases/uc-win-09-track-submissions.md) | Main flow → 2a. Someone else's proposal is requested by ID | The API rejects it. |
| `CP-WIN-41` | [`UC-WIN-09`](use-cases/uc-win-09-track-submissions.md) | Main flow → 4a. The proposal has a linked wine | The person can open it. |
