# Pruebas

Casos de prueba del módulo: uno por el flujo principal de cada caso de uso y uno por cada flujo alternativo. Se pueden ejecutar a mano en la web y en la app; la columna de tests automáticos indica qué tests ejercen el caso de uso.

## Casos de prueba

| ID | Caso de uso | Pasos | Resultado esperado |
|---|---|---|---|
| `CP-LEG-01` | [`UC-LEG-01`](use-cases/uc-leg-01-legal-centre.md) | 1) La persona abre el centro legal (`/legal`, en la web y en la app). 2) El cliente lista los documentos: términos, privacidad, política de contenidos, moderación, confianza y seguridad, ranking, pagos y cancelaciones, y cookies. 3) La persona elige uno. 4) Para los términos, el cliente pide la versión vigente a la API en el idioma de la interfaz; el resto de los documentos viene incluido en el cliente. 5) El cliente muestra el documento con su versión. | La persona leyó el documento; leer no registra ninguna aceptación. |
| `CP-LEG-02` | [`UC-LEG-01`](use-cases/uc-leg-01-legal-centre.md) | Flujo principal → 4a. La API no responde al pedir los términos | Se muestra la copia incluida en el cliente, marcada como no confirmada, con opción de volver a cargar. |
| `CP-LEG-03` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | 1) La persona abre el registro y el cliente carga los términos vigentes. 2) El cliente muestra los términos plegados, la casilla desmarcada y el enlace a la política de privacidad. 3) La persona puede desplegar el texto y marca la casilla. 4) Al enviar el registro, el cliente agrega `termsAcceptance` con versión, idioma, hash y `accepted: true`. 5) La API compara la selección con la versión vigente antes de crear la cuenta. 6) La API crea la cuenta y guarda la aceptación en la misma transacción ([UC-USR-01](../users/use-cases/uc-usr-01-sign-up.md)). | La aceptación queda guardada con versión, idioma y hash, en la misma transacción que crea la cuenta. Aceptar los términos no activa cookies opcionales ni comunicaciones promocionales. |
| `CP-LEG-04` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Flujo principal → 1a. Los términos no cargan | Se avisa con «Volver a cargar términos» y el registro no se puede enviar. |
| `CP-LEG-05` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Flujo principal → 3a. La casilla no está marcada | El formulario no se envía. |
| `CP-LEG-06` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Flujo principal → 5a. La versión o el hash ya no son los vigentes | La API responde 422 `TERMS_VERSION_CHANGED`, no crea la cuenta, y el cliente muestra un mensaje traducido, recarga los términos y desmarca la casilla. |
| `CP-LEG-07` | [`UC-LEG-02`](use-cases/uc-leg-02-accept-at-sign-up.md) | Flujo principal → 1b. La persona se registra con Google o Apple desde esa pantalla | No se envían términos y se piden después del ingreso ([UC-LEG-04](use-cases/uc-leg-04-accept-current-version.md)). |
| `CP-LEG-08` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | 1) La persona entra a una parte privada de la aplicación o a completar el perfil. 2) El control de términos pide el estado de aceptación a la API. 3) Mientras espera muestra «Verificando tu cuenta…». 4) La API calcula el estado: si la cuenta aceptó la revisión vigente, no hace falta aceptar; si aceptó una revisión anterior y el plazo de aviso no venció, tampoco, e informa la fecha límite (`requiredFrom`); en otro caso hace falta. 5) Si no hace falta aceptar, el cliente muestra la aplicación. | El cliente sabe si hace falta aceptar los términos; la aplicación solo se muestra si no hace falta. |
| `CP-LEG-09` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Flujo principal → 4a. Hace falta aceptar | Se sigue con [UC-LEG-04](use-cases/uc-leg-04-accept-current-version.md). |
| `CP-LEG-10` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Flujo principal → 2a y 2b. La consulta falla | Sin conexión o por tiempo de espera, la app muestra «Sin conexión» con ilustración y «Reintentar»; por otro motivo, «No pudimos verificar tu acuerdo» con opción de volver a cargar. En ningún caso se muestra la aplicación ni se da por hecho que faltan términos. |
| `CP-LEG-11` | [`UC-LEG-03`](use-cases/uc-leg-03-check-acceptance.md) | Flujo principal → 1a. La persona abre el centro legal o contacto | No se controla la aceptación (en la web se excluyen esas rutas; en la app están fuera del grupo privado `(app)`). |
| `CP-LEG-12` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | 1) El cliente muestra «Antes de continuar» con los términos plegados y la casilla desmarcada. 2) La persona marca la casilla. 3) Pulsa «Aceptar y continuar». 4) El cliente envía versión, idioma, hash y `accepted: true`. 5) La API compara la selección con la versión vigente y guarda la aceptación. 6) La API devuelve el estado confirmado y el cliente muestra la aplicación. | La aceptación queda guardada con cuenta, revisión, versión, idioma, hash y fecha asignada por PostgreSQL. El acceso se libera solo después de la confirmación de la API, y vale en todas las plataformas. |
| `CP-LEG-13` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Flujo principal → 5a. La versión cambió mientras tanto | La API responde 422 `TERMS_VERSION_CHANGED`, el cliente desmarca la casilla y pide volver a cargar; nunca reintenta la aceptación solo. |
| `CP-LEG-14` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Flujo principal → 4a. Falla la red | Se muestra el error con «Volver a cargar términos» y no se libera el acceso. |
| `CP-LEG-15` | [`UC-LEG-04`](use-cases/uc-leg-04-accept-current-version.md) | Flujo principal → 5b. La revisión ya estaba aceptada (otro dispositivo o doble envío) | La API no duplica nada, conserva la primera fecha e idioma y devuelve el estado. |
| `CP-LEG-16` | [`UC-LEG-05`](use-cases/uc-leg-05-decline-and-sign-out.md) | 1) La persona pulsa «Ahora no · cerrar sesión». 2) El cliente cierra la sesión ([UC-USR-08](../users/use-cases/uc-usr-08-sign-out.md)). 3) La persona vuelve a la parte pública. | La sesión se cierra y no se registra ninguna aceptación. El centro legal y contacto siguen disponibles. |
| `CP-LEG-17` | [`UC-LEG-05`](use-cases/uc-leg-05-decline-and-sign-out.md) | Flujo principal → 2a. El cierre de sesión falla | Se muestra «Volvé a intentar cerrar sesión.». |
| `CP-LEG-18` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | 1) La tarea programada corre 60 segundos después del arranque y luego cada 300 segundos. 2) Lee la versión vigente y calcula su fecha límite. 3) Toma con bloqueo el cursor de la revisión y busca las próximas 500 cuentas a avisar, ordenadas por id. 4) Encola un aviso `TERMS_UPDATED` por cuenta con clave de idempotencia `terms-updated:<revisión>:<cuenta>`. 5) Guarda la última cuenta avisada como nuevo cursor. 6) El módulo de [notificaciones](../notifications/README.md) envía el email con la plantilla `terms_updated`. | Cada cuenta activa y no bloqueada que aceptó una revisión anterior, y no la vigente, recibe un único aviso `TERMS_UPDATED` con la versión y la fecha límite. El avance queda guardado en `legal_terms_announcements`. |
| `CP-LEG-19` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | Flujo principal → 2a. No hay fecha límite o ya venció | La tarea no hace nada. |
| `CP-LEG-20` | [`UC-LEG-06`](use-cases/uc-leg-06-announce-terms-update.md) | Flujo principal → 3a. Quedan menos de 500 cuentas | Se marca la revisión como completa y las corridas siguientes no buscan más. |
| `CP-LEG-21` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | 1) El cliente llama a un endpoint autenticado. 2) El interceptor consulta el estado de aceptación de la cuenta. 3) Si no hace falta aceptar, la petición sigue normalmente. | Las cuentas que deben aceptar no pueden usar la API autenticada hasta hacerlo. |
| `CP-LEG-22` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Flujo principal → 3a. Hace falta aceptar | La API responde 422 `TERMS_ACCEPTANCE_REQUIRED` («Review and accept the current terms to continue»). |
| `CP-LEG-23` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Flujo principal → 1a. La ruta está excluida (`/auth/**`, `/legal/**`, `/support/**`, `/notifications/unsubscribe`, salud, documentación de la API y `/uploads/**`), la petición es anónima o es `OPTIONS` | Pasa sin consultar. |
| `CP-LEG-24` | [`UC-LEG-07`](use-cases/uc-leg-07-enforce-acceptance.md) | Flujo principal → 1b. Es `DELETE /users/me` o `DELETE /users/me/permanent` | Pasa sin consultar. |
| `CP-LEG-25` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | 1) El equipo escribe una migración Flyway que inserta en `legal_documents` las filas `es` y `en` con la misma versión y revisión, y el SHA-256 de cada texto. 2) Despliega el backend y la migración se aplica. 3) Cambia `LEGAL_TERMS_VERSION` a la versión nueva. 4) Los clientes reciben la versión nueva al pedir los términos. | La versión nueva queda archivada y es la vigente. Si cambió la revisión contractual, las cuentas deben volver a aceptar según [UC-LEG-03](use-cases/uc-leg-03-check-acceptance.md). |
| `CP-LEG-26` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | Flujo principal → 1a. Es una corrección editorial equivalente | Se publica una versión nueva con la misma revisión y nadie tiene que volver a aceptar. |
| `CP-LEG-27` | [`UC-LEG-08`](use-cases/uc-leg-08-publish-terms-version.md) | Flujo principal → 1b. Es un cambio sustantivo | Se usa una revisión nueva; las cuentas que aceptaron la anterior tienen el plazo de aviso y reciben [UC-LEG-06](use-cases/uc-leg-06-announce-terms-update.md). |
